# v0.1.0 — a coding agent that works

**Status:** M0 done · **Written:** 2026-09-06 · **Follows:** nothing

The first version, and the bar it has to clear is **stable enough to run daily and to test the
concept**. Everything wired: the packages, the local MCP server, skills, the working tree, the
todo list, and a terminal you can actually hold a conversation in.

## What this version is for

Proving the idea works, not making it beautiful. Those are different jobs and this version is only
the first one.

**Correct beats polished, and that is a real instruction rather than a hedge.** Every event
variant renders, every card can be answered, nothing lies about what happened, `NO_COLOR` and a
pipe both produce something legible. What is *not* in scope is the design language of
[`docs/tui.md`](../tui.md) fully realised — the ocellus beat, the collapsed-block tails, the
diff renderer, the syntax palette, the `^K` overlays. That is v0.2.0 M1, and it is deferred because
a beautiful terminal in front of a loop nobody has driven for a week is polish spent on the wrong
thing.

`docs/tui.md` still governs everything built here. The parts of it this version implements, it
implements as written — the colour meanings, the gutter, the 68-column measure, the card wording.
It is scope that is reduced, not the standard.

## A note on the numbers

M2 and M3 swapped, and M1 of v0.2.0 is new. `docs/versions/README.md` says a milestone keeps its
number — that rule is about not renumbering **after work has started**, because it would make every
commit message and status entry referring to the old number wrong. Only M0 has commits, and it kept
its number. Nothing else had been started, referenced or branched, so the renumbering costs nothing
and this paragraph is the record that it happened.

## The milestones

### M0 — the workspace ✅

The repository skeleton and every document. Vendored packages with `packages/VENDOR.md`, the uv
workspace, ruff / `mypy --strict` / pytest / coverage, pre-commit, CI, and the four meta-tests
(layering, workspace shape, docs, vendor).

**Why it was this large.** The four meta-tests are what stop this repository quietly becoming
something else. `test_layering.py` is what makes ADR 1's claim about the foundation packages
checkable; `test_vendor.py` makes *a vendored package is not edited* a build failure. Writing them
after the code would have meant writing them against code that had already violated them.

The finding worth carrying forward: **no vendored package needed a line changed.** Everything
hera-code redirects was already injectable, and `SLOT_PROJECT` takes everything about a working
tree. If that stops being true, [ADR 1](../adr/0001-a-uv-workspace-with-heras-packages-vendored.md)
is what to re-open.

### M1 — the spine

One turn, end to end, with no terminal.

- `hera-code init` seeds the **shared** `~/.hera` — `mind/`, `skills/`, `mcp.json` — and
  hera-code's own `~/.hera/code`. Nothing is overwritten; somebody who already runs hera keeps
  what they have, and somebody who has never run it gets a working install either way.
- `hera-code check` reports whether the directories are usable, and says what to do when they are
  not.
- `config.toml` for registered endpoints, seeded from `HERA_*` environment variables the first time
  it is written — so an existing `HERA_PROVIDER_BASE_URL` is already filled in. After that the file
  wins: a setting you can change and that quietly does not apply is worse than one that overrides a
  variable.
- `wiring.py` assembles provider · prompt builder · skill router · tool registry · orchestrator.
- A `coding` profile, and the project-slot preamble that carries the coding register. The mind
  regions stay shared and generic — if a sentence would still be true in a chat window it is a mind
  region, if it would not it is project text.
- Alembic owns the sessions schema in `apps/cli`.
- `hera-code -p "…"` runs one turn and prints the answer.

**Skills are wired here**, not later: `hera_skillsets.SkillRouter` is already in the turn loop, so
M1 is where `~/.hera/skills` gets seeded and pinned skills start arriving. `/slash` and the skill
gutter row need a terminal and land in M3.

**`-p` before the terminal, deliberately.** It is the whole turn loop with none of the rendering,
so a bug found in M3 has an unambiguous answer to *is this the loop or the drawing*. It is also
what CI drives and what a script uses.

### M2 — the tools, and the local MCP server

`hera_code_mcp` built for real, mounted in-process through `hera_tools` under the name `code`, plus
`hera_code_workspace` underneath it.

- Files: `read`, `write`, `edit` (find/replace), `glob`, `grep`.
- Shell: `bash`.
- `ask` — the tool that is never run, recognised by `hera_chats` through
  `ChatsSettings.asking_tools`.
- Root discovery, branch and dirty count, `.gitignore`-aware walks, and the containment guard.
- `AGENT.md` / `AGENTS.md` / `CLAUDE.md` at the root, composed into `SLOT_PROJECT`.

**The default permission policy lands here and is decided before anything is wired.** Navigate and
read `allow`, write and edit `ask`, `bash` `ask`, anything outside the working tree `deny`. hera
allows her own tools without a card because they are bounded; nothing about that reasoning survives
a tool with a shell in it.

**One thing to settle in this milestone rather than discover:** what an `ask` outcome means in
`-p` mode, where there is nobody to answer. A card that cannot be drawn must not silently become an
allow. The answer is almost certainly *the turn closes with `awaiting_permission` and the exit code
says so*, plus a `--yes` flag that is documented as what it is.

After M2, hera-code can do work. It cannot yet be steered while doing it.

### M3 — the terminal

Functional, not finished. Built to [`docs/tui.md`](../tui.md), scoped to what a person needs to
hold a conversation:

- The transcript in real scrollback and the pinned dock — [ADR 3](../adr/0003-the-transcript-lives-in-scrollback.md).
- **One renderer per `ChatEvent` variant**, and an unknown one degrades visibly. Tested by
  rendering each through a recording console and asserting on the export — that is what makes the
  rule checkable rather than asserted.
- The activity gutter: verb, target, duration, and **why** a skill was selected.
- The permission card and the question card, both answerable.
- `/slash` commands and `@file` completion.
- The theme with a light set, `NO_COLOR`, and the non-TTY path.
- The re-render from the persisted list at `turn_closed`.
- `^C` cancels the turn and keeps the work so far.

Deferred to v0.2.0 M1 and named here so the deferral is visible rather than forgotten: the ocellus
beat, collapsed-block tails, the diff renderer, the syntax palette, the `^K` overlays, and the
sub-80-column dock.

### M4 — the todo list

`hera_code_todos`, `TODOS.md`, `todo_read` / `todo_write` / `todo_set`, the always-visible dock
strip with `^T`, and **the intake conversation** — the agent asks before it plans, using the `ask`
suspension from M2, and writes the list with the person.

**After M3 because the intake is a conversation**, and a conversation needs question cards that can
be answered. In `-p` mode there is no intake; the list is read and followed if it exists.

This is the milestone that makes hera-code *steerable*, which is the thing the whole design is
organised around — [ADR 8](../adr/0008-the-todo-list-is-a-file-and-the-intake-is-a-conversation.md).

### M5 — sessions

`--continue`, `--resume <id>`, a session picker, and a compaction pass when the history outgrows
the window. A coding session runs for hours; M1 through M4 all assume it survives being closed.

### M6 — the release

PyInstaller for macOS arm64 and x86-64, Linux x86-64 and arm64, Windows x86-64. `release.yml`
already has the tag-versus-`pyproject.toml` check and a job that fails pointing here.
`install.sh` and `install.ps1`. A smoke test that runs the built binary's `--version` on each
runner, because a binary that does not start is the failure a source-based test cannot find.

**A tag that fails on one platform fails the release** rather than shipping four. A partial release
is worse than a late one: the person who gets the missing platform cannot tell it from a network
problem.

## Not in v0.1.0

- **The visual pass** — v0.2.0 M1. Scoped out on the maintainer's call: prove the concept, then
  make it beautiful.
- **The shadow tree, sketches and thoughts** — v0.2.0 M2. The most interesting feature here, and it
  is worth nothing until the file tools it hangs off are stable. Every dependency arrow points into
  it.
- **The code graph** — v0.2.0 M3. tree-sitter grammars are the largest single contributor to binary
  size, and M6 should ship something small once before it ships something large.
- **hera reaching hera-code over a transport** — v0.3.0. It should need no change in hera at all,
  which is a claim worth verifying deliberately rather than in passing.
- **`hera_memories`** — v0.2.0 M4.
- **Nested `AGENT.md` discovery.** Root-level only; the lookup is written to grow into it.
- **A sandbox.** v0.3.0, and it is one question with two callers — hera's ADR 15 asks it too, and
  answering it twice is how two answers diverge.

## Order, and where it is arguable

M0 → M1 → M2 → M3 → M4 is a real dependency chain: the loop before the tools, the tools before the
terminal that draws their cards, the terminal before the conversation that fills the todo list.

**The one genuinely arguable place is M2 before M3.** Building the tools with only `-p` to drive
them means every permission card is untested until M3, and permission is the part of M2 most likely
to be wrong. The alternative — terminal first — means building card renderers with no real calls to
render. Neither is clean; this order was chosen because a wrong card is visible the moment M3 lands,
and a wrong loop under a pretty terminal is not.

M5 and M6 are independent of each other. If M6 is ready first it goes first, and this paragraph is
why that would not be a change of plan.
