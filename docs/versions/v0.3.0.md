# v0.3.0 — reachable

**Status:** planned, not started · **Written:** 2026-09-06 · **Follows:** v0.2.0

The version where hera-code stops being only a thing a person types into.

## M1 — hera reaches hera-code

`hera-code serve` exposes `hera_code_mcp` over streamable HTTP on localhost. hera reaches it as an
entry in `~/.hera/mcp.json`:

```json
{ "mcpServers": { "hera-code": { "url": "http://127.0.0.1:8787/mcp" } } }
```

**The claim this milestone exists to verify is that hera needs no change at all.** hera already
reads that file, and `hera_tools` already mounts whatever it finds there without knowing what it
is. If that holds, remote control of a coding agent is a document and a binary rather than a
feature — and hera's own
[v0.3.0 document](https://github.com/VoidEUW/hera/blob/main/docs/versions/v0.3.0.md) predicted
exactly this. Worth verifying rather than assuming, which is why it is a milestone and not a
sentence in a README.

It works because of a decision taken in M0: `hera_code_mcp` imports no other package in this
workspace and takes everything as a port
([ADR 4](../adr/0004-mcp-is-the-tool-layer.md)). Serving it is a change of transport, not a
rewrite. That is the whole return on a rule that cost something to hold for two versions.

**What is deliberately not in scope: talking to a *remote* hera.** "From far away" is a different
security posture from "on this machine", and the second is where this starts. `serve` binds
`127.0.0.1` and there is no flag to change it in this version.

## M2 — the permission posture for a server with a shell

The question M1 opens, and it is a permissions question rather than a transport one.

`hera__*` is allowed without a card in hera because it is hers and bounded. **Nothing about that
reasoning extends to a CLI with a shell in it**, reached over a socket, acting on a working tree.
The default policy for `hera-code__*` seen from hera's side is not the default policy for
`code__*` seen from inside hera-code, and treating them as one is how a card that should have
appeared does not.

**This wants deciding before it is wired, not after** — so M2 is an ADR and a default, and it
gates M1 being documented as ready rather than following it.

The specific things to answer: whether a call arriving over the transport is distinguishable from
one made locally (it must be), whether hera's permission cards are an adequate place to make these
decisions (a diff does not fit on one), and what a session even means when two front ends can
drive the same working tree at once.

## M3 — where code runs

A sandbox. This is **one question with two callers**: hera's
[ADR 15](https://github.com/VoidEUW/hera/blob/main/docs/adr/0015-running-code-in-a-container.md) is
written and deferred, and it asks the same thing hera-code's `bash` tool asks. Answering it twice
is how two answers diverge.

The right shape is probably a package hera-code owns and hera vendors, or the reverse — but that is
a packaging decision that follows from the answer rather than preceding it, and this repository has
opinions about vendoring ([ADR 1](../adr/0001-a-uv-workspace-with-heras-packages-vendored.md)) that
should be brought to that conversation rather than discovered during it.

## Not decided

**The order.** M2 gates M1's documentation, and M3 is independent of both. Whether the sandbox
should come first is a genuine question: it is the thing that would make `bash` allowable without a
card, which is the single biggest friction in daily use — and daily use is what finds the things a
plan cannot.

That ordering is what this document gets next, once v0.2 has been used for long enough to say which
of them is missing most.
